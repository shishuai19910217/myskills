## 1. 背景与现状

「智慧农业物联网平台」中已存在「AI 助手 / 智能问答 / 智能方案」三个入口界面，**当前全部为假页面，无真实实现**。

用户当前获取农技知识的途径：自己询问专家、查找网上资料、或沿用既往经验 [C4]。平台在这一环上没有提供任何能力。

| 现状项 | 状态 |
|---|---|
| 前端界面 | 假页面 |
| 后端 AI 服务 | 不存在 |
| 知识库内容 | 为空；来源尚未确定 [C7] |
| 目标用户 | 大棚农户 |

---

## 2. 问题定义

农户遇到病虫害、种植问题时缺少可信的、随手可得的农技指导；平台缺少把农技知识送达农户的能力。

**关键风险事实**：农户拿到答案后，**既有人直接照做执行**（喷药、施肥、调整温湿度），**也有人只当参考资料再找专家确认** [C10]。这意味着错误答案存在直接造成生产损失的可能。

---

## 3. 目标与非目标

### 3.1 本期目标

在 8 周内，用 Java 技术栈亲手跑通一套「知识库优先 → 库外兜底 → 来源强制标注 → 幻觉可观测」的问答机制，并**能对每一个环节讲清「它在干什么、为什么这么设计、不这么做会怎么坏」** [C6]。

### 3.2 明确的非目标

本期**不做**以下内容（留待上线前）：

- 生产级高可用、多租户、权限体系
- 增量索引管理、切片版本与失效清理
- 知识库内容运营后台
- 自动化评测平台
- 平台前端真实对接（保持本地实验形态）

> 理由：本期交付标准是「跑通 + 讲清」。过早引入生产级复杂度会稀释有限的学习窗口。

## 4. 交付物与验收标准

本期共 5 条成功标准，全部可自证：

| # | 标准 | 达成判据 |
|---|---|---|
| S1 | 最小 RAG 闭环能跑 | 灌入 1 个 .docx，问一个库内问题，能答出且带来源 |
| S2 | 库外分流能跑 | 问一个库外问题，能进入兜底分支并输出「知识库外」标记 |
| S3 | 六环节可拆解讲解 | 能不看代码讲清：解析 → 切块 → 向量化 → 检索 → 重排 → 生成+引用，各自的失败模式 |
| S4 | 对比实验记录 | 至少 1 组对照实验（切块尺寸），记录「哪个更好 + 为什么」 |
| S5 | 失败案例分析 | 至少 1 个「库里有但没召回」的真实失败案例 + 归因 |

**资源预算**：每周 5 小时 × 8 周 = 40 小时 [C23 保守假设]。
> 原始方案估 96–152 小时，超预算 2–3 倍，因此必须裁剪（见 §7）。

## 5. 技术路线选型

### 5.1 候选方案对比（真实分叉）

| 维度 | **方案一（采用）Spring AI 纯 Java** | 方案二 Dify/RAGFlow 自建 + Java 走 HTTP | 方案三 Java 主控 + Python 检索微服务 |
|---|---|---|---|
| 白盒可拆解 | 高，Advisor 链可逐环节断点 | **低，黑盒** | 中 |
| 单一语言 | 是 | 是 | 否，双进程 |
| Word 解析 | TikaDocumentReader 现成支持 | 最强（DeepDoc） | 强 |
| PPT 解析 | 结构丢失，见 §8 风险 R3 | 最强 | 强 |
| 落地成本 | 低（单工程） | 中（Docker + HTTP） | 高 |
| 支撑「讲清每个环节」 | 直接支撑 | **直接冲突** | 部分支撑 |

### 5.2 选型结论

**采用方案一**。核心理由（按权重）：

1. **白盒可拆解** —— 直接服务于 S3「能讲清每个环节」这一交付标准 [C6]
2. **Java 栈一致** —— 与现有平台技术栈统一 [C11]
3. **Word/PPT 有现成解析器** —— `TikaDocumentReader` 基于 Apache Tika，官方文档确认支持 DOC/DOCX、PPT/PPTX、PDF、HTML

**被否决的原因**：
- 方案二：黑盒平台学不到检索层细节，与 S3 冲突
- 方案三：双语言双进程，对缺少工程落地经验的人失败面翻倍 [C3]

### 5.3 已核实的 API 事实

以下为官方文档核实结果，非推测：

| 事实 | 来源 |
|---|---|
| `TikaDocumentReader` 支持 PDF / DOC / DOCX / PPT / PPTX / HTML | Spring AI 1.0.x `TikaDocumentReader` API 文档 |
| 该 Reader **「直接返回纯文本，不保留任何格式」** | 同上 |
| `QuestionAnswerAdvisor` 支持 `similarityThreshold` / `topK` | Spring AI RAG Reference 1.0 |
| `ContextualQueryAugmenter` 提供 `allowEmptyContext(false)` 开关 | Spring AI RAG Reference 1.0 |
| 召回文档可经 `chatClientResponse().context().get(QuestionAnswerAdvisor.RETRIEVED_DOCUMENTS)` 取回 | spring-ai issue #1747，维护者回复 |
| `DocumentPostProcessor` 是重排的挂载点 | Spring AI RAG Reference 1.0 |
| **依赖坐标在不同参考文档中不一致** | 1.0.x 参考文档写 `spring-ai-advisors-vector-store`，后续版本参考文档写 `spring-ai-vector-store-advisor` |

> 最后一条构成一个执行风险：以实际拉取到的版本为准，不依赖高级 Advisor 链用法。详见 §8 风险 R1。

## 6. 核心机制设计：幻觉治理四层

### 6.1 先纠正一个认知偏差

原始诉求是「用 RAG 验证大模型的回复是否正确、减少幻觉」[C6/C9]。

**RAG 不能验证回复是否正确，它只能让模型「有据可依」。**
「标注来源为知识库外」只改变答案的**外观**，不改变答案的**正确性**；反而会让农户看到一个「有出处」的答案，更容易相信它。仅靠这一条机制，幻觉风险并未实质下降。

### 6.2 四层防线

| 层 | 机制 | 解决的问题 | 挂载点 |
|---|---|---|---|
| **L1 检索闸门** | 显式 `similarityThreshold`，把「库里没有」变成可测量的数字 | 「库外」不再靠模型感觉 | `SearchRequest` |
| **L2 生成分流** | 三级模板分流（见 6.3） | 库外场景的直接误导性输出 | 三套 `PromptTemplate` |
| **L3 引用闭环** | 召回切片的文件名+块号注入 prompt 标号；答案中的 `[来源N]` 与实际召回列表做二次比对，对不上则降级为库外 | 模型伪造引用 | `RETRIEVED_DOCUMENTS` |
| **L4 观测闭环** | 落库：问题 / 答案 / 命中切片 / 相似度 / 是否兜底 / 人工抽检结论 | 把幻觉问题转成**内容运营问题** | 自建问答流水表 |

### 6.3 L2 三级分流（不可一刀切）

一刀切「禁止输出剂量」的规则过粗，会把「有害的错误答案」换成「无害的没用答案」，农户体验反而更差。故改为三级：

| 级别 | 判定条件 | 模板行为 |
|---|---|---|
| ① 库内命中 | 相似度 ≥ 阈值且召回非空 | 严格基于 context 作答，必须带 `[来源N]` |
| ② 库外但有通用方向 | 未达阈值，但存在可给的方向性判断 | 保守模板：**允许方向性建议，禁止具体数值与商品名** |
| ③ 库外且无方向 | 未达阈值且无可给方向 | 明确告知知识库未覆盖，引导联系农技专家 |

三级分界**用测试集实测决定，不拍脑袋**。

### 6.4 L4 的关键指标：两个维度交叉看

**兜底率是过程指标，不是结果指标。** 兜底率低只说明知识库覆盖好，风险仍可能极高——因为**库内内容本身就是错的** [C7 内容来源未定]。

因此问答流水表必须记录两个维度并交叉分析：

| 兜底率 | 抽检错误率 | 诊断 | 处置 |
|---|---|---|---|
| 高 | 低 | 知识库覆盖不足 | 补内容（可解） |
| 低 | 高 | **知识库内容质量危机** | **RAG 架构救不了，必须人工重写内容** |
| 高 | 高 | 知识库基本无效 | 暂停上线，回到内容侧 |
| 低 | 低 | 健康 | 正常 |

## 7. 实施策略与阶段划分

| 阶段 | 目标 | 估时（5h/周版） | 裁剪动作 |
|---|---|---|---|
| 阶段 1 | 最小闭环跑通 + 建评测集 | 6–8 h | 评测集 10 条压到 8 条 |
| 阶段 2 | 真文档对照实验 | 8–10 h | 只做切块尺寸 1 组，砍掉 embedding 对照；PPT 只验证能否抽正文，不验证表格 |
| 阶段 3 | 幻觉治理四层落地 | 10–12 h | **不裁剪** |
| 阶段 4 | 评测与讲清交付 | 6–8 h | 砍评测集扩充，保留失败案例分析 |
| 合计 | | **30–38 h** | 卡在 40h 预算内 |

**裁剪原则：砍 S4（对比实验），绝不砍 S3（幻觉治理四层）。** S3 才是真实交付物。

**并行任务（不可串行）**：首批 `.docx` 内容采集必须与技术阶段**并行**推进。内容侧不落实，后面全部卡死（风险 R2）。

## 8. 风险登记册

| ID | 风险 | 触发条件 | 概率 | 防死手段 | 回退方案 |
|---|---|---|---|---|---|
| **R1** | Spring AI 版本间 API 差异导致 Advisor 链不可用 | 依赖坐标不一致，高级 API 签名变化 | 30% | 只用最小 API 面：`TikaDocumentReader` + `vectorStore.similaritySearch` + 手工拼 prompt，不依赖 Advisor 链高级用法 | 切方案二（Dify + HTTP），保住 S1/S2 |
| **R2** | **内容侧落空** —— 知识库是空的或不可用 | 「内容由谁写」始终没落实 | **45%** | 首批 5 份 .docx 设为阶段 1 并行任务 | 无回退，此风险不可接受，必须前置解决 |
| **R3** | PPT/表格解析残缺，用药信息召回不全 | 首批内容用 PPT 承载且表格是核心载体 | 25% | 首批**默认只收 .docx/.md**；PPT 降级为待验证项 | 解析层换 MinerU / Docling / RAGFlow，检索与生成层不动 |
| **R4** | 库外兜底变成「无害的废话」 | L2 一刀切 | 20% | L2 三级分流（§6.3） | 收紧到只保留 ① 和 ③ |
| **R5** | 时间不够，阶段 3 被砍 | 每周投入不足 5h | 30% | 砍 S4，保 S3 | 顺延周期，S3 未完成不算交付 |

**最高优先级**：R2。它不是技术风险，是内容风险，且 RAG 架构救不了。

## 9. 明确不适用场景

本方案**不适用**以下三种情况，硬套会失败：

| # | 场景 | 失败模式 | 应改用什么 |
|---|---|---|---|
| 1 | 农技内容高度依赖表格与图示（用药量对照表、营养元素表、症状图谱） | 解析丢失结构，召回残缺，引用再准确也是「残缺的准确」 | MinerU / Docling / RAGFlow 做解析层 |
| 2 | 需要多跳推理（「A 作物在 X 温度下的 Y 病害用什么药」要跨 3 份文档关联） | 纯向量 topK 召不齐片段，模型拿不到完整链条 | GraphRAG / LightRAG / KAG，不要硬调 topK |
| 3 | 农技指导需专家高频修订、每天有新增与作废 | 最小实现无增量索引、版本管理、失效切片清理 | LlamaIndex 索引管理 / RAGFlow 编排层 |
