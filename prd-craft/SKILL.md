# prd-craft — 模糊想法 → PRD 文档

> **别名**：产品需求孵化器 / PRD 打磨器 / 想法到文档。
> **目标**：把"一句话灵感"或"一份零散材料"变成一份**结构完整、需求可验证、研发和业务都能直接用**的 PRD 文档；或对已有 PRD 做对抗式评审。
> **正确性来源**：不是 AI 自报的掌握度百分比，而是【**约束清单逐条打钩确认** + **认知四象限显式交付**】。确证 = 用户签收，不是自评。
>
> 🧭 **核心元原则：先挖后判** —— 在挖掘弄清真实诉求之前，严禁输出任何方案、PRD 章节或预判。挖透，再动手。

---

## 一、什么时候用（适用边界）

**✅ 做**：
- **模式 A · 萌芽孵化**：输入是模糊感觉（"感觉团队知识沉淀可以优化"），要产出一份全新 PRD。
- **模式 B · 梳理升级**：输入是已有需求文档 / 零散功能清单 / 会议纪要，要整理补全成结构化 PRD。
- **模式 C · 评审验证**：输入是一份已存在的 PRD，要评审其完整性、可验证性、边界漏洞，产出评审报告。

**❌ 不做**（直接回答即可，不引入流程）：
- 一句话 API 参数 / 语法 / 简单查询；
- 需求已完全清晰、用户只想快速套个文档壳 → 走 B 模式**快速通道**（见阶段 1）；
- 已越过需求阶段的纯技术实现讨论 → 用 correctness-enhanced-reply 或直接讨论。

> 与其他 skill 的边界见文末【与 correctness-enhanced-reply 的定位差异】。

---

## 二、全局纪律（贯穿模式 A / B / C 全流程，违反 = 输出作废）

| # | 纪律 | 含义 |
|---|---|---|
| G1 | **一问一答、单轮单问** | 每轮只输出 1 个精准问题。一次抛 ≥2 个问题 = 违规 |
| G2 | **一正一反交叉提问** | 单数轮问【正向诉求】（想要什么/目标），偶数轮问【反向约束】（不想要/限制/边界）。交替推进，摸清边界 |
| G3 | **先挖后判** | 挖掘阶段严禁给方案、预判、PRD 章节草稿。挖透并确证后才输出 |
| G4 | **确证达标才输出** | 产出 PRD 前，必须先完成【约束清单】逐条打钩确认；不自报"95% 置信度" |
| G5 | **最终交付附认知四象限** | 产出末尾附加【认知四象限】（确定的/不确定的/需确认的/盲区），用户确认后才算交付完成 |
| G6 | **多角度对抗审查** | 产出前做红队自查（Pre-Mortem + 反向查漏 + 可验证性核对） |
| G7 | **先确认再落盘** | PRD 正文先在对话内产出并获用户确认 → 才落盘文件 |

> **例外（唯一允许打破 G1/G2 的情形）**：G2 的反向轮在模式 A 的**前 2 问**暂不生效——萌芽期用户连"想要什么"都没想清时，先连续 2 问正向，从第 3 问起严格执行正反交替（对应 Pre-Mortem 死因 #2 的防御）。

## 三、执行总览（四阶段 + 主导权切换）

```
输入 → 阶段 0：输入模式判定（A/B/C）→  ← 入口判定，独立于决策树
  ├─ A 萌芽孵化 → 阶段 1A：全维度深挖
  ├─ B 梳理升级 → 阶段 1B：预解析 + 缺口挖掘 + 收敛
  └─ C 评审验证 → 阶段 1C：评审检查表（不挖需求，改审 PRD）
  → 阶段 2：约束清单整理 + 用户逐条打钩
  → 阶段 3：产出（PRD 标准骨架 / 评审报告）→ 对抗审查 → 认知四象限
  → 阶段 4：对话确认 → 落盘
```

**主导权切换**：
- AI 主导：阶段 0（判定）、阶段 1（提问）、阶段 3（产出与自查）
- 用户主导：阶段 1 每轮答案确证、阶段 2（打钩）、阶段 3（审查结果评审）、阶段 4（确认落盘）

> **硬约束**：阶段 1 未挖透、阶段 2 未获用户全部打钩之前，**严禁**输出任何 PRD 章节内容。

## 四、阶段 0 — 输入模式判定（独立于决策树）

判定 A/B/C，两种方式，**用户自报优先**：

1. **用户自报**：用户明确说"我这是要评审" / "把这份需求理成文档" / "帮我把这个想法展开" → 直接对应 C / B / A。
2. **兜底启发式**（用户没自报时，据输入形态判定）：

| 输入形态 | 判定 |
|---|---|
| 仅模糊感觉 / 一句话想法，无成型材料 | → **A 萌芽孵化** |
| 有需求文档 / 功能清单 / 会议纪要等成型材料 | → **B 梳理升级** |
| 附有已写好的 PRD 文档 | → **C 评审验证** |
| **混合**（模糊想法 + 半份清单） | → 判为 **A 派生物**：按 A 走深挖，产出时把输入里的清单类信息**合并**进对应章节 |

> 判定完后向用户简要声明一句（"我将按【A 萌芽孵化】模式带你走"），若用户有异议即改。判定结果不归决策树管（C9）。

## 五、阶段 1 — 需求决策树问答（核心引擎）

### 5.1 决策树是什么（内部机制，**不展示给用户**）

- 决策树是 skill 的**隐性问题调度中枢**：根据用户上一轮的回答，决定下一问走哪个分支、哪个维度尚未覆盖，保证提问**穷尽、不重复、不留盲区**。
- 用户只能看到"一个精准问题（+ 必要时一行小字说明问它为了什么）"，**永远看不到树的结构 / 当前分支 / 维度清单**。
- 决策树只在**模式确定之后**做节点选择（C9）；4 个方法论（5W2H / 苏格拉底 / 双钻 / 利益相关人）是树上的**节点策略库**——每个节点决定"这个维度该怎么问"。

### 5.2 维度网格（节点库 + 每个维度的正/反问题策略）

决策树从以下维度节点取材。**最小必需维度集**（对应 PRD 标准骨架，须覆盖到）用 ★ 标注；其余为**条件追加维度**（回答暴露相关信号才问，防止过度提问）。

| # | 维度节点 | 归属策略 | 【正向诉求】怎么问（想要什么） | 【反向约束】怎么问（边界/不想要） |
|---|---|---|---|---|
| ★V1 | 问题 / 背景 | 5W2H | 你要解决的具体问题是什么？ | 这个问题现在不动，最坏会怎样？ |
| ★V2 | 目标 / 成功标准 | 5W2H | 做成后可验证的结果是什么？ | 哪些结果是你明确**不追求**的？ |
| ★V3 | 目标用户 | 5W2H | 谁会用它？核心人群是谁？ | 谁是你明确**不服务**的？ |
| ★V4 | 使用场景 | 5W2H | 在什么场景、什么时机下用？ | 哪些场景你明确**不做**？ |
| ★V5 | 功能清单 | 双钻收敛 | 它需要具备哪些功能？（此刻先发散，不排优先级） | 哪些功能你**坚决不要 / 已否决**？ |
| ★V6 | 优先级 / MVP | 双钻收敛 | 第一版必须包含的核心功能是哪些？ | 哪些功能可后置 / 是**绝对不可砍**的底线？ |
| ★V7 | 边界与例外 | 苏格拉底 | 正常流程之外有什么特殊情况？ | 什么情况下本功能**明确不做 / 不适用**？ |
| ★V8 | 验收标准 | 5W2H | 一条功能完成，用什么标准验收？ | 哪些验收方式你**不接受**？ |
| maxV9 | 时间窗口 | 5W2H | 想什么时候上线？里程碑节点？ | 哪些时间点有**硬性限制 / 不可接受**？ |
| V10 | 成本 / 资源 | 5W2H | 预算、人力投入的上限是多少？ | 哪些资源**绝对不能占用**？ |
| V11 | 技术约束 | 5W2H | 现有系统 / 技术路线有什么限制？ | 哪些技术手段被**禁止**？ |
| V12 | 非功能（性能/安全/合规） | 5W2H | 有性能、安全、合规要求吗？ | 哪些合规红线**不能碰**？ |
| V13 | 收益与指标 | 5W2H | 上线后用什么指标衡量成功？ | 哪些指标你**不在乎 / 不考核**？ |
| V14 | 数据 / 隐私 | 5W2H | 需要采集哪些数据支撑功能？ | 哪些数据因隐私**不能碰**？ |
| V15 | 隐藏需求 | 苏格拉底 | 除了刚才说的，还有什么没出口的需求？ | 之前同类方案**失败 / 被骂**的经历？ |
| V16 | 利益相关人 | 利益相关人 | 谁拍板？谁会被影响？谁可能有异议？ | 哪些人的**反对会推翻本方案**？ |

### 5.3 路由算法（每轮如何决定下一问）

AI 在内部维护三个状态，**不展示**：

- **S**：已覆盖维度集（含"已覆盖但待补充"标记）
- **f**：正反标志位（f 每轮翻转；模式 A 前 2 问强制 f=正）
- **P**：追加候选队列（由回答暴露的新维度）

每轮动作（严格单轮单问）：
1. **候选维度** = （★ 最小必需集 − S）∪（P − S）。若候选为空 → 进入阶段 2。
2. **选维度**：取当前**信息增益最高**（最影响 PRD 成形、用户回答最薄）的未覆盖维度。
3. **提问**：按 f 标志，用该维度对应策略问【正向】或【反向】question；若该维度只有一个方向有信息差，可用另一方向补。
4. **应答四分类 → 更新**：
   - **明确** → 记入约束清单（来源 [用户明说]），S += 该维度。
   - **模糊 / 不知道** → 打标"待补充"跳过（不阻塞），S += 该维度（标"待补充"），继续问能答的维度。
   - **暴露新方向** → 把新信号映射到追加维度（如用户谈到合规 → V12；谈到被某部门卡 → V16），push 进 P。
   - **回答矛盾**（与前面冲突）→ **不得自行二选一**，表面冲突并请用户裁决。
5. **f 翻转**（f = 正 ↔ 反）；P 中已被 S 覆盖的弹出。
6. **苏格拉底强化**：对关键回答可叠加一次反诘（"你说『____』，如果『____』反例呢？"）或动机追问（最多 3 层，只追动机不扩维度）。计入轮数、不额外增问。

### 5.4 方法论节点策略（4 个策略如何被树调度）

| 策略 | 调度时机 | 动作 |
|---|---|---|
| **5W2H** | 发散层主体，覆盖 V1-V4/V8-V14 | 补全背景、目标、人、时、成本、收益、非功能维度 |
| **苏格拉底拷问** | 任一关键回答落定后（可选叠加） | 反向追问链：反诘用户原句 + 对"边界/例外/反面"连问，堵漏洞（≤3 层） |
| **双钻收敛** | 功能发散（V5）到 3 条以上后 | 从发散切收敛：砍到 MVP，产出功能取舍清单（V6） |
| **利益相关人对齐** | 进入阶段 2 前的最后一轮（V16） | 探测各方期望冲突 → 记入约束清单 → PRD 的风险/约束章节 |

### 5.5 模式差异（同一棵树，三种走法）

| | 模式 A 萌芽孵化 | 模式 B 梳理升级 | 模式 C 评审验证 |
|---|---|---|---|
| 起点 | 从零挖，全部 ★ 维度都可能问 | **预解析输入文档** → 从文档提取已覆盖维度塞进 S → 只问缺口维度 | 不挖需求 → 直接进入评审检查表（见 5.6） |
| 轮数上限 | **≤ 20 问** | **≤ 15 问** | **≤ 15 项核查** |
| 裁剪 | — | 多余细节（字段命名等）自动补全，不与用户逐字对 | 只针对"漏洞/缺口"展开，不逐条重述 |
| 进入阶段 2 时机 | 最小必需集全覆盖 且 用户无补充 | S 覆盖所有从文档提取不到的 ★ 维度 | 评审检查表跑完 |

**B 模式快速通道**：若输入文档本就完整（章节齐全），跳过缺口挖掘 → 直接阶段 2 整理 → 阶段 3 产出。用户明确要"快速套壳"时启用。

**C 模式替代 5.2/5.3**：C 模式不走维度问答，改走下面的评审检查表。

### 5.6 C 模式：评审检查表（对已有 PRD 逐项对抗审查）

对输入 PRD 逐项审查，每项给出「✅ 通过 / ⚠️ 缺口 / ❌ 错误」，只针对问题展开追问：

| # | 审查项 | 查什么 |
|---|---|---|
| C1 | 目标可验证性 | 成功标准是否可测量，还是空话 |
| C2 | 范围纪律 | 功能是否发散过度 / MVP 是否清晰 |
| C3 | 边界与例外 | 异常场景、反面案例是否缺失 |
| C4 | 功能可验收性 | 每条功能是否带可执行验收标准 |
| C5 | 非功能完整性 | 性能 / 安全 / 合规是否漏 |
| C6 | 隐性假设 | 有哪些"没写出来但默认成立"的假设 |
| C7 | 风险自识 | 方案是否自识风险，还是全凭信心 |
| C8 | 数据与隐私 | 数据采集 / 隐私边界是否交代 |
| C9 | 利益相关人冲突 | 各方期望冲突是否被识别 |
| C10 | 需求可溯源性 | 每条需求能否追溯到"为什么做" |

> C 模式产出 = **评审报告**（格式见 7.6；阶段 1 简化为"按审查项逐项核 + 输出缺口清单"）。

### 5.7 收敛与终止

- **正常收敛**：最小必需集全覆盖（或 C 检查表跑完）→ 询问用户"以上是我的预设问题，你是否还有其他要补充？"（意图不明时追问 1 次）。用户确认"没有" → 阶段 2。
- **轮数上限**：A≤20 / B≤15 / C≤15。到顶还差关键维度 → 输出："目前确证度不足（缺：____）。我可以先出**草案 PRD**（缺口标待确认），或你补齐 ____ 后我再正式输出。" 由用户二选一。
- **严重信息不足**（连续 3 轮回答离题 / 关键维度用户无法补全 / 连续 3 次拒答）→ 直接终止：
  ```
  ⚠️ 我无法给出可靠 PRD，因为缺少以下关键信息，硬编会误导你：
  1. ____  2. ____  3. ____
  补全后可重新进入流程，或我们先就某部分展开。
  ```

## 六、阶段 2 — 约束清单整理 + 用户逐条打钩

### 6.1 整理【约束清单】

把阶段 1 所有回答提取为约束条目，**每条标注来源标签**：

- `[用户明说]` / `[用户估计·未验证]` / `[AI 推断·需验证]` / `[文档提取]`（B 模式从输入文档提取）/ `[沉默默认]`

按分组罗列：**A 输入与模式 / B 方法论内核 / C 交互纪律 / D 产物与交付 / E 风险与假设**。

### 6.2 认知四象限自查（清单整理后，先自查再交付）

把来源标签的零散信息收拢成四类，**盲区不瞎编**：
```
· 我确定知道的（用户明说 / 有依据）：____
· 我还不确定的（需验证）：____
· 需要你确认的（已放入约束清单）：____
· 盲区（我不知道自己不知道的 → 交给验证或用例暴露）：____
```

### 6.3 逐条打钩

输出完整清单，请用户逐条确认（"全部确认"或指出编号修正）。**全部打钩后方可进入阶段 3。** 自评"已经懂了 XX%"不作数。

---

## 七、阶段 3 — 产出（PRD 或评审报告）

进入前输出：
```
✅ 需求挖掘阶段结束。
以下是经你逐条确认的【约束清单】（共 N 条，含来源标签）。
【元原则声明】基于已确证的约束清单，下面按 __（模式 A/B/C）__ 产出。
```

### 7.1 PRD 标准骨架（模式 A / B 共用模板 · 双受众适配）

> 摘要层给管理层/业务方（1 页内），正文层给研发/产品。若标准骨架未覆盖的新章节由决策树发现，**动态追加**（见 7.2）。

```
【摘要层 · 一页读懂】（管理层/业务方优先）
· 一句话定位：____
· 背景与要解决的问题：____
· 目标与成功度量：____
· 重点收益与优先级：____
· 资源需求与风险概要：____

【正文层 · 研发/产品】
1  需求概述 & 业务背景
2  目标用户 & 使用场景
3  功能需求（每条含：功能描述 / 验收标准 / 优先级标注）
4  边界与例外（异常场景、反面案例、不适用场景）
5  非功能需求（性能 / 安全 / 合规）
6  技术约束 & 依赖（现有系统限制、禁止项、依赖项）
7  优先级 & 版本规划（MVP 范围 + 后续迭代）
8  数据 & 埋点指标（采集项 / 隐私边界）
9  风险 & 开放问题（利益相关人冲突、待确认项、假设清单）
```

### 7.2 动态追加章节规则

- 标准骨架为基础；决策树若发现骨架未覆盖的新维度（如用户谈到了国际 / 多语言、冷启动、渠道），**追加对应章节**，编号顺延。
- 追加以"回答确有该信息"为前提，不得为凑章节硬加。

### 7.3 AI 建议补全规则（配合"待补充"跳过）

对阶段 1 中被标记"待补充"的缺口、或用户在产出阶段未定的部分：

- AI **主动补一版默认值**，**必须标注**「AI 建议：____（推断，需确认）」；
- 用户可修改或留空。低风险字段（字段命名、章节组织）可径直接为建议值；**高风险决策（优先级、功能取舍、资源承诺）只给建议值，强制用户裁决**——不得当作事实写入。

### 7.4 多角度对抗审查（产出正文后，交付前）

对刚产出的 PRD/评审报告做三轮自查，发现即改（改完无需输出全部草稿，直接给最终版）：
1. **Pre-Mortem**：假设已上线且失败，列出最可能的 3-5 个死因 → 每条约"触发条件 + 防死手段"。若 PRD 未覆盖，补进【风险】章节。
2. **反向查漏**：对每条核心功能问"反例是什么？" → 漏掉的边界补进【边界与例外】。
3. **可验证性核对**：每条功能是否都带可执行验收标准；没有的一律补上或标待确认。

### 7.5 认知四象限（最终输出必附）

在 PRD/评审报告末尾附加 G5 的四象限，作为交付签收界面。

### 7.6 C 模式：评审报告格式（替代 7.1-7.5 的 PRD 正文）

```
【评审结论】整体评价：通过 / 有条件通过 / 打回
【逐项核查结果】C1-C10 表格（✅ 通过 / ⚠️ 缺口 / ❌ 错误 + 一句说明）
【漏洞清单】（按严重度排，每条：漏洞 / 触发场景 / 建议修正）
【可验证性核对】不可验收的需求清单
【修订建议】优先改什么（若用户要直接出修订版 PRD，走 7.1 标准化）
【认知四象限】
```

## 九、与 correctness-enhanced-reply 的定位差异

本 skill **完全自治**，不调用其他 skill（C16）。但为避免用户混淆，以下划清边界：

| 维度 | prd-craft | correctness-enhanced-reply |
|---|---|---|
| 产出物 | **PRD 文档 / 评审报告** | 决策 / 技术方案 / 结论 |
| 输入 | 模糊想法 / 需求材料 / 已有 PRD | 复杂问题 / 高代价决策 |
| 核心机制 | 需求决策树 → 约束清单 → 标准骨架 PRD | 提问挖掘 → 约束清单 → 方案比对 |
| 三模式 | A 孵化 / B 梳理 / C 评审 | 单模式（高可靠决策） |
| 何时用 | 要"一份文档" | 要"一个最优决定" |

> 简单查询两者都不进流程；技术实现讨论用 correctness，产品需求成文用本 skill。

## 十、典型失败模式 & 防御

| 失败模式 | 行为 | 防御 |
|---|---|---|
| 提问一轮抛多个问题 | 一轮问 5 个 | 强制 G1，只保留最关键 1 个 |
| 正反交叉失效 | 连问多轮正向 | G2 翻转标志；A 模式第 3 问起强制交替 |
| 决策树展示给用户 | 用户看到"当前走 x 分支" | 5.1 铁则：路由永远隐性，用户只见问题 |
| 萌芽期过早反向 | A 模式第 2 问就问"不想要什么" | 例外条款：A 前 2 问固定正向 |
| 挖掘无底洞 | 用户每答都引入新分支，永不收敛 | 5.7 轮数上限 + 到顶出草案 |
| 用户答不上来就卡死 | 卡在一个维度无法推进 | 5.3 打标"待补充"跳过（C12/C14 配合） |
| 占位符留白 | 用户没想好的部分产 PRD 留白 | 7.3 AI 建议补全（带"需确认"标注） |
| 用户确认没做就打钩 | 把"我觉得行了"当确证 | 6.3 逐条打钩是硬闸门，不自报百分比 |
| 范围死守骨架不加章 | 新维度硬塞进旧章节 | 7.2 动态追加原则 |
| 先给结论 | 挖掘半途就吐 PRD 章 | 元原则先挖后判 + 硬约束 |
| 忘记认知四象限 | 交付物没有四象限 | G5 强制 |
| 输出完就落盘 | 未确认直接写文件 | G7 先确认再落盘 |

## 十一、验证方式（本 skill 自身）

- **三角用例回归**：每次改版后跑 A/B/C 三个冒烟用例（模糊想法 / 零散清单 / 已有 PRD），确认三条路径都收敛。
- **轮数收敛检查**：每 10 次使用统计平均问答轮数（目标 A≤20 / B≤15 / C≤15）；超了就是决策树覆盖判定太贪，需收紧★最小必需集。
- **确证签收率**：记录用户对认知四象限的"确认"比例。若用户频繁说"这个我没说过"（盲区没标出来），说明四象限诚实度下降。
- **返工率**：落盘后被用户打回的 PRD 比例。若高，说明 6.3 打钩环节走过场，需再收紧。
