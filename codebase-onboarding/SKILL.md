# codebase-onboarding — 陌生系统认知与安全二开 Skill

> **目标**：对当前工作目录下的源代码执行系统性、全面的静态分析与架构梳理，产出带行号证据的分层认知资产（L0–L6），并在聚焦模式/二开前按需产出功能认知卡（L7）与影响半径清单，支撑“看懂系统”和“安全二开”两个动作。
> **交付物**：3 份分析文档 + 1 份导航（`docs/ai-onboarding/`，可通过 `output_dir` 参数覆盖）。
> **正确性来源**：证据逐条可追溯——每条结论挂 `文件:行号`，无证据不写，不确定显式标注 `[推断]` / `[待确认]`。

---

## §0 一句话定位

把陌生/遗留代码库转化为带行号证据的分层认知资产（L0–L6），并在此基础上按需产出功能认知卡（L7）与影响半径清单；支撑“看懂系统”和“安全二开”两个动作。静态分析只兑现结构事实，运行事实一律标注并附验证方法，不编造。

---

## §1 适用 / 不适用

**做**：陌生/遗留单仓或多模块代码库静态逆向；架构梳理；新人 onboarding；业务链路梳理；二开前影响半径评估。

**不做（直接回答）**：无源码仅二进制 → `reverse-engineer-anything`；改代码本身（改 Bug/实现功能）；从零设计新系统；纯前端视觉走查；替代真实业务决策；无权限连生产取 APM/binlog/MQ（只出标注，不出结论）。

## §2 输入参数

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `repo_path` | 否 | 当前工作目录 | 目标代码库路径 |
| `output_dir` | 否 | `docs/ai-onboarding` | 输出目录，须独立于源码文件，防循环论证 |
| `focus` | 否 | 全量 | 业务域/链路关键词，命中者优先；亦为聚焦模式触发条件 |
| `business_hints` | 否 | — | 业务背景、术语表、外部系统说明 |
| `output_depth` | 否 | `full` | `full`=全量 L0-L6；`layer`=指定层级；`single`=单功能深挖 |

用户未指定 `repo_path` 时直接分析当前工作目录，不卡确认。

**`output_depth` 分支与聚焦模式的关系**（Stage 2 判定，Stage 4 生效）：

| `output_depth` | 产出范围 | 与聚焦模式（`focus`/“要改要加”）的关系 |
|---|---|---|
| `full`（默认） | 全量 L0–L6 | 非聚焦；`focus` 仅作命中优先级 |
| `layer` | 仅用户指定层级（如“只给我 L2”只产出 L2） | 可叠加：指定层级内若提“要改/要加”，该层附 L6 |
| `single` | 单功能深挖：该功能相关的 L2/L3 + L6 影响半径 + L7 功能卡 | 是聚焦模式的子集，默认按聚焦模式处理 |

**`output_dir` 唯一确认点的动作**（防循环论证）：`output_dir` 若与源码目录重合或位于源码树内，先提示用户“建议输出到源码树外（默认 `docs/ai-onboarding`）；不改则产出会与源码混放，本轮将自动排除该目录以防循环论证”，然后按用户答复执行；用户不答复时仍用默认值继续，不阻塞分析。另见 R1。

## §3 核心原则（违反 = 产出作废）

- **R1 只读不改**：只读命令，禁止 Edit/Write 源码、禁止 `git checkout/reset/clean`、禁止装依赖、禁止起服务。唯一写入范围 = `output_dir`。读到密钥/token 一律脱敏，明文绝不进文档。
- **R2 证据可追溯**：每条结论附 `相对路径:行号`。无法追溯的不写，留 `[推断]`/`[待确认]`，不编。否定性结论（“无数据库/无测试”）用搜索记录作证据，格式见 §7.3。
- **R3 codegraph 作辅助**：codegraph 给出的调用链/影响面优先于 grep 推断，但不能作为唯一来源；结论须回到 Read 实读代码校验，冲突时以代码原文为准；codegraph 不可用时走兜底路径，不中断，并在 README 注明。
- **R4 全覆盖 + 覆盖率声明**：分析前先数清总文件数；分析后 README 写明覆盖率（已分析 X / 总 Y，未覆盖范围与原因）。禁止“读了一部分却写成全面分析”。
- **R5 双模式**：全量模式为默认；聚焦模式（用户给 `focus` 或提“要改/要加”）时，README 必须写“聚焦范围 X/Y，非全覆盖”，且 L6/L7 按需产出（见 §6、§12）。

## §4 执行 SOP（六阶段；每阶段：动作、分支与降级、完成判据、落盘点）

| 阶段 | 动作 | 分支与降级 | 完成判据 | 落盘点 |
|---|---|---|---|---|
| Stage 1 预扫描 | 数文件总量（覆盖率分母）→ 技术栈/入口/数据载体/配置/测试 → 应用排除清单 → 落 L0 草稿 | 无源码仅二进制 → 直接回答不适用，终止 | 入口清单与技术栈明细完整 | L0 草稿 |
| Stage 2 模式判定 | 全量（默认）vs 聚焦（`focus` 参数/用户提“要改/要加”） | 用户未指定 focus 时不卡确认，直接全量 | 模式已定且记录 | README 声明 |
| Stage 3 链路定位 | 按入口**存在性**（非频次）列候选链路 | 系统仅一两条时写明判定依据；频次数据缺失时不编造 | 链路候选清单 + 判定依据 | 入口清单附记 |
| Stage 4 分层产出 | L0→L6 逐层，每层先写信息来源范围声明，每条结论挂 `文件:行号` | L7 仅聚焦模式/二开前产出；缺运行材料的层写“缺层+原因+补齐路径”，不阻塞 | 每层落盘且每条结论有来源 | 每层立即落盘 |
| Stage 5 验证标注 | 静态给不了的运行事实统一标注 + 附验证方法（一套标注体系，见 §9） | 运行时材料缺失时只标注，不出结论 | 运行时结论 100% 带验证方法 | 验证清单 |
| Stage 6 自检交付 | 现 §7.4 五条 + 新门禁（去除强制编造项）→ 按 §11 格式汇报覆盖率与待确认 Top 5 | 门禁不满足则不宣称完整交付 | 自检 5 条全通过 | 最终汇报 |

### 4.1 工具：codegraph 作辅助，Read/Grep/Glob 实读为准

codegraph 可加速取链路、影响面、符号关系；**但所有写进文档的结论必须以实读代码为最终依据**。

| 要采集的信息 | 辅助：codegraph 命令 | 兜底：实读（Read/Grep/Glob） |
|---|---|---|
| 全量文件清单（算 R4 覆盖率） | `codegraph files -p <repo> --format flat` | `find`/Glob（排除清单见 §4.3） |
| 符号源码 + 调用路径 | `codegraph explore "<符号名或问题>" -p <repo>` | Read + Grep |
| 函数级调用栈 | `codegraph callers <symbol>` / `codegraph callees <symbol>` | Grep 调用方符号 |
| 代码变更影响范围 | `codegraph impact <symbol> -d 3` | Grep 符号名 + 逐个读调用方 |
| 接口定义与实现映射 | `codegraph explore` + `query -k class -k interface` | Glob `*Controller/*Router/*Mapper` + Read |
| 模块间依赖 | `codegraph files` 目录结构 + import/require 语句 | Grep `^import\|require\|from ` |

索引不存在时（目标仓库无 `.codegraph/`）：① 先问用户是否允许 `codegraph init <repo>`（会在仓库内创建 `.codegraph/`）；② 不允许 → 直接 Read/Grep/Glob 兜底，不中断分析，README 注明“未用 codegraph，调用链为静态推断”；③ 允许 → 建索引后继续，索引目录**不得作为证据来源**。

### 4.2 六类核心信息（逐项采集，缺项要写明“不适用”）

1. 模块依赖关系：模块边界、谁依赖谁、有无循环依赖
2. 跨模块调用链路：直接 import / HTTP / MQ / 共享文件 / 事件
3. 函数级调用栈：核心函数完整 caller → callee 链
4. 代码变更影响范围：改某个核心函数/表/接口波及哪些模块（用 `impact` 取证）
5. 接口定义与实现映射：定义位置 ↔ 实现位置 ↔ 调用方
6. 文件覆盖清单：全部源码文件 + 每个文件一句话职责（核对 R4）

### 4.3 排除清单与读取纪律

- 全程排除：`node_modules` `.git` `dist` `target` `build` `vendor` `coverage` `*.min.js` `bak`/`*.bak`，**以及 `output_dir` 本身**（否则把自己上一轮写的文档当证据，循环论证）。
- 运行时巨型产物（如 `data/*.json`）禁止整读，只取键名，任一可用运行时即可（JSONL 行文件只取首行键名，不整读）：
  - Python：`python -c "import json;print(list(json.load(open('f.json')).keys())[:20])"`
  - Node：`node -e "console.log(Object.keys(require('./f.json')).slice(0,20))"`
  - 二者都不可用时：`head -c 2000 f.json` 看片段（不整读）+ 标 `[待确认]`，不中断分析。
- 双份目录（`src/` 与 `dist/` 内容重复）一律只引 `src/` 作证据。
- 技术栈与版本必须取自依赖文件实际声明（`package.json`/`pom.xml`/`go.mod`/`requirements.txt`/`Cargo.toml`，含版本号），取不到写 `[待确认]`，不得凭记忆补。

## §5 输出格式（3+1 文件；每篇单文件 ≤400 行，超长拆分）

- **README.md**：导航 + 阅读路线（快速 10 分钟 / 完整 1 天）+ 覆盖率声明（R4 强制）+ 三条最重要结论 + 待确认问题 Top 5。
- **01-architecture.md**：架构总览（一句话定位 / Mermaid 架构层级图 / 技术栈明细含版本 / 模块层级划分 / 模块间依赖图 + 清单 / 跨模块调用规则 / 核心函数级调用栈 / 变更影响范围 5~10 个核心符号 / 已知结构风险）。
- **02-business-flows.md**（最可能超长）：Part A 核心业务链路全景（链路总表 + 每条链路节点图 Mermaid + 逐节点七列说明 / 异常分支 / 事务边界与失败补偿）；Part B 系统功能详细清单（功能总表全量，入口一条不漏 + P0 功能六项详析：执行流程图 / 业务链路时序图 / 数据表与状态流转 / 端到端数据流转 / UML 类图或时序图 / 证据汇总）。功能数 >15 时拆 `02a-core-flows.md`（链路）+ `02b-function-list.md`（功能清单）。
- **03-data-api-map.md**：数据载体总览（含无 DB 降级：文件 JSON / 内存 Map / 外部 API / 日志 / 环境配置）/ 表结构明细 / 数据操作矩阵（C/R/U/D/S）/ 状态机汇总 / 接口定义与实现映射 / 端到端数据流转 / 跨服务一致性 / 变更数据影响面。

四份文档的逐节模板（骨架、列定义、P0 六项详析）见 `references/output-spec.md`，按模板落盘，不得自行删节。

| 层 | 内容大纲 | 信息来源（静态） | 运行时验证项 |
|---|---|---|---|
| L0 系统概览 | 定位 / 技术栈 / 模块 / 入口清单 / 外部依赖 | package.json/pom.xml、路由文件、Job 配置、MQ 配置 | Swagger 页面、MQ 控制台（缺失则标注） |

| L6 影响半径清单 | 仅聚焦模式/二开前产出：9 列模板（变更点/调用方/被调用方/数据表/字段/MQ topic/配置项/权限点/回滚降级，缺字段写“—”不省略列）+ 补充列（缓存 key/定时任务/报表/灰度/测试范围按需追加）；三步法：双向追踪+横向扫描+环境评估；扩展点优先级：配置 > SPI/插件 > 继承/接口 > 切面 > 改源码。模板见 `references/output-spec.md` L6 节 | 调用链/依赖图/配置/权限/环境 | 配置中心运行值为运行时项，缺失则标注 |

## §7 质量标准

### 7.1 硬性要求（5 条）

1. 与代码完全一致：所有技术细节、业务逻辑描述必须与代码实际实现一致。禁止信息遗漏、逻辑偏差、主观臆造。
2. 无证据不写：抽任意 10 条结论，每条都能在 `文件:行号` 处找到对应原文。找不到的要么补证据，要么标 `[待确认]`。
3. 三级标注：无标注 = 有代码证据；`[推断]` = 基于上下文推测，须写明**为什么推断**；`[待确认]` = 代码里查不到，须写明**向谁确认 / 如何验证**。运行时结论在标注后追加验证方法，格式：`结论 [待确认：<验证方法>]`。
4. 不可留空：小节如果该系统不适用（如无数据库、无认证），必须写“不适用声明 + 为什么”，不能跳过空节。
5. 文档 ↔ 代码一致性：凡发现仓库自带文档与代码矛盾，即记 `[文档不符]` 并注明**以代码为准**。

### 7.2 无数据库系统的降级规则（不允许留空表）

载体类型：`文件JSON` / `内存Map` / `外部API` / `日志` / `环境配置`。数据表结构改为载体**键结构**；操作矩阵列名改为 `[文件]xxx.json` 这类带类型前缀的载体名；文档开头写一行“本系统无数据库，以下载体即数据存储层”。

无事务系统：不写空节，改写“不适用声明 + 一致性风险表”：

| 载体 | 风险场景 | 现状 | 影响 | 建议 | 证据 |
|---|---|---|---|---|---|
| meeting-*.json | 写到一半进程崩溃 → 文件损坏 | 无原子写（未先写临时文件再 rename） | 该会议数据丢失 | 改 tmp+rename | src/snapshot.ts:27 |

### 7.3 否定性结论的证据格式（“无 X”没有行号可挂，但这类结论往往最有价值）

至少覆盖 **2 类线索**（正向 grep + 反向 glob）并列出实际用过的命令；必须给出**替代实现**（“没有 X，但用 Y 实现”）；搜索模式覆盖不全时降级为 `[待确认]`，写明“已排除 A/B/C，未排除 D”。

示例：

```markdown
### 本系统无数据库
- **搜索记录**：Grep `@Entity|@Table|mysql|prisma|sequelize|typeorm` → 0 命中
- **反向佐证**：Glob `**/migration*/**`、`**/*.sql`、`**/schema.*` → 0 个文件
- **替代实现**：持久化全在 `src/snapshot.ts:27-33`（写 JSON 到 `data/meetings/`）
- **可信度**：高（已覆盖 ORM/SQL/迁移/Schema 四类线索）
```

### 7.4 交付前自检（5 条，逐条核对）

1. 4 份文档全部存在且非空；
2. README 已写明 **覆盖率**（已分析 X/Y 文件 + 未覆盖范围与原因）——R4；
3. **抽样 10 条结论**逐条回查 `文件:行号`，全部命中；
4. 每个源码模块在 `01` §4 有对应行；每个入口在 `02` 功能总表有对应行 —— R4；
5. 所有不适用小节都写了“不适用声明”，无跳过的空节；密钥已脱敏。

## §8 信息分层（主体 vs references/ vs examples/）

- **主体 SKILL.md**：角色、目标、适用不适用、输入参数、核心原则、执行 SOP、输出格式、L0–L7 层规范、质量标准、门禁、已知坑、最终汇报格式——工程师触发技能时直接读，控制在单文件 ≤400 行。
- **references/**：output-spec（L0–L7 详细规范与可复制模板，内嵌而非 8 个碎片文件）、verification-checklist（9 项运行时验证清单 + 静态兑现边界表，整表正文在 `references/verification-checklist.md`）、impact-analysis（影响半径三步法 + 扩展点优先级 + 按需产出规则）、anti-patterns（已知坑去重合并）——按需检索，避免一次性倾倒。
- **examples/**：至少 1 条完整链路样例，供对齐与教学。

## §9 统一标注体系（裁决结果）

全文一套标注，不得并存两套：

- 无标注 = 有代码证据
- `[推断]` = 基于上下文推测，须写明**为什么推断**
- `[待确认]` = 代码里查不到，须写明**向谁确认 / 如何验证**

运行时结论在标注后追加验证方法，格式：`结论 [待确认：<验证方法>]`。废弃 HTML 方案的 `【待验证】` 并存写法。

## §10 已知坑与应对（合并去重）

| 坑 | 应对 |
|---|---|
| 大仓库上下文溢出 | Step 1 先数规模；每完成一份立即落盘；`impact`/`explore` 只查核心符号，不做全量符号枚举 |
| 静态分析抓不到动态行为 | 动态分发/反射/配置化路由 → 结合测试与日志线索，标 `[待确认]`，**不硬猜** |
| 接口定义与实现对不上 | 四处交叉验证：路由定义、实现函数、`*Mapper.xml`/`@Select`、`CREATE TABLE` |
| 业务规则代码里没有 | 不编。在对应文档写 `[待确认]` 并在 README 待确认清单交业务方 |
| 把自己产出的文档当证据 | 全程排除 `output_dir`（§4.3） |
| 把 `dist/` 当代码 | 只引 `src/`，在 README 注明双份关系 |
| 改公共代码当低风险 | 横向扫描 + Call Hierarchy，评估连锁故障 |
| 不更新文档 | 二开后强制回灌 `references/anti-patterns.md` |
| 把菜单当功能地图 | L1 必须含角色与链路，菜单仅作参考 |
| 只画静态图不验证 | 每层附验证清单，运行时结论标注 + 验证方法 |

## §11 最终汇报格式

产出：4 个文件 → `<output_dir>`；覆盖率：已分析 X / 共 Y 个源文件（未覆盖：范围与原因）；核心链路：N 条 · 核心功能：N 个 · 数据载体：N 个。

六类核心信息采集自检（对照 §5.5 逐项，未采全的写明原因）：
1. 模块依赖关系
2. 跨模块调用链路
3. 函数级调用栈
4. 代码变更影响范围
5. 接口定义与实现映射
6. 文件覆盖清单（核对 R4：全部源码文件 + 每个文件一句话职责）

系统一句话定位；三条最重要结论（各附证据）；待确认问题 Top 5（各附“向谁确认 / 如何验证”）；未覆盖 / 需人工确认的地方。

## §12 质量门禁裁决表（不逼编造的合法出口）

| 门禁项 | 判定标准 | 状态 |
|---|---|---|
| 来源标注 | 每层输出前均有信息来源文件/目录 | 必过 |
| 运行时标注 | 运行时依赖结论全部标注 + 验证方法，100% 覆盖 | 必过 |

| 影响半径可执行 | 聚焦模式下 L6 表格字段齐全；非聚焦模式默认不产出 L6，不阻塞交付 | 必过 |
| 禁止编造 | 无“通常/一般”等无来源结论 | 必过 |

## §13 关键 SOP 步骤（可直接执行、可验收）

1. **预扫描**：数源文件总量（覆盖率分母）→ 识别技术栈/入口/数据载体/配置/测试 → 应用排除清单 → 落 L0 草稿。无源码则直接回答不适用。
2. **模式判定**：全量（默认）或聚焦（用户给 `focus` 或提“要改/要加”）。不卡确认；聚焦模式在 README 写“聚焦范围 X/Y，非全覆盖”。
3. **链路定位**：按入口存在性列候选链路；仅一两条时写明判定依据；供用户可选确认，不中断。
4. **分层产出**：L0→L6 逐层，每层先写信息来源声明，每条结论挂 `文件:行号`，每层立即落盘。L7 仅按需产出。
5. **验证标注**：静态给不了的运行事实统一标注 + 附验证方法（单套标注体系）。
6. **自检交付**：执行 §7.4 五条 + §12 门禁；汇报覆盖率与待确认 Top 5；门禁不满足不宣称完整。
