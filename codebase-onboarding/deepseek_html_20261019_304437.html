陌生系统认知与二开 Skill · 设计方案

把陌生代码库转化为可指导二开的结构化认知资产 —— 一份可复用、可验证、可迭代的 AI Agent Skill 设计文档。

Skill 名称：legacy-system-onboarding 版本 v1.0 七层结果物 AI 辅助 + 运行时验证

1. 概述与定位

1.1 一句话定位

Skill 定位
一个面向「刚接手陌生系统平台的软件工程师」的 AI Agent Skill：输入一个代码仓库，输出一套分层的、带来源标注的、可被运行时信号验证的认知资产，直接支撑功能新增、老功能迭代与影响半径评估。

1.2 解决的问题

缺口具体表现本 Skill 的应对
认知完整性缺口不知道"了解一个系统"要覆盖哪些维度强制七层结果物规范
AI 结果物缺口知道用 AI 分析，但不知道让它输出什么固定输出模板 + 结构约束
真实验证缺口静态分析可能漏运行时信息每层附带验证清单，标注"待验证"
二开映射缺口从认知到安全修改缺方法功能认知卡片 + 影响半径清单

1.3 适用 / 不适用

✅ 适用
接手陌生后端/全栈系统；需要二开前评估影响；需要给团队沉淀系统认知文档；需要让 AI 稳定产出结构化分析。
❌ 不适用
从零设计新系统；纯前端视觉走查；无代码库只有黑盒；需要替代真实业务决策的场景。

1.4 设计原则

  1. 先地图后道路：先知道有什么，再深入怎么跑。
  2. 先主流程后分支：先跟 3–5 条核心链路，再看异常与补偿。
  3. 先动态后静态：运行时信号优先于纯代码推断。
  4. AI 是助手不是真相：每层必须可被验证，不确定标"待验证"。
  5. 影响半径 = 双向依赖 + 数据流 + 事件流 + 配置/权限 + 环境。

4. 工作流设计

Skill 内部采用 5 阶段 + 7 层输出 的工作流。阶段是执行节奏，层级是产物结构。

4.1 五阶段执行流程

① 预扫描→ ② 核心链路定位→ ③ 七层产出→ ④ 标注待验证→ ⑤ 交付与自检
阶段动作产出
① 预扫描识别技术栈、模块、入口类型、外部依赖；运行 scan 脚本L0 草稿、入口清单
② 核心链路定位基于入口、表、MQ 频次推断 3–5 条核心链路，与用户确认链路候选清单
③ 七层产出按 L0→L7 顺序产出，每层标注来源文件七层结果物
④ 标注待验证对运行时依赖项标注"待验证"，附验证方法验证清单
⑤ 交付与自检按质量门禁自检，输出最终文档包可交付认知资产

5.2 角色与目标

你是一名资深系统架构分析师与代码考古专家。
你的目标：帮助刚接手陌生系统的软件工程师快速建立整体认知，
并产出可直接指导二开、功能修改、新增与迭代优化的结构化认知资产。

5.3 工作步骤（核心指令）

1. 预扫描：识别技术栈、模块、入口、外部依赖，运行 scripts/ 下扫描脚本。
2. 定位核心链路：结合入口频次、核心表、MQ 主题，推断 3–5 条核心链路，
   与用户确认后再深入。
3. 按 L0 → L7 逐层产出，每层必须先声明信息来源（文件/目录），
   再按 templates/ 对应模板输出。
4. 对依赖运行时才能确认的结论，统一标注【待验证】，并给出验证方法。
5. 交付前按 references/verification-checklist.md 与质量门禁自检。

5.4 输出硬性要求

  • 每层输出前，先写信息来源（如：src/order/controller/）。
  • 不确定处必须写【待验证】，禁止编造。
  • Mermaid 图必须语法正确、可直接渲染。
  • 优先覆盖核心链路，不做全量穷举。
  • 表格字段必须齐全，缺失字段写"—"而非省略。

5.5 禁止事项

硬性禁止
① 不读运行时材料却宣称完整；② 用"通常""一般"替代具体来源； ③ 跳过用户确认直接展开全部链路；④ 输出无法验证的笼统结论； ⑤ 把菜单当成业务功能地图的全部。

7. 运行时验证机制

AI 基于静态代码分析，容易漏掉运行时信息。Skill 必须内置验证清单，并对运行时依赖项强制标注【待验证】。

7.1 验证清单

验证项验证方法对应层级
入口是否全对比 Swagger、路由文件、Job 配置、MQ 配置L0、L1
链路是否全看日志、APM、链路追踪、抓包L2
分支是否全看枚举类、状态迁移代码、DB 实际值L3
表是否全看数据库 schema、Mapper/XML、RepositoryL4
谁写谁读搜表名、看 SQL 日志、binlogL5
MQ 是否全看 MQ 控制台、配置文件、消费者注解L0、L2、L5
定时任务是否全看 xxl-job、Quartz、@ScheduledL0、L2
外部依赖是否全看配置文件、HTTP 客户端、SDKL0
影响半径是否全IDE Call Hierarchy、grep 反向查L6

7.2 标注规范

【待验证】使用规则
凡结论依赖运行时信息（真实 MQ 主题、动态配置、外部回调、DB 实际状态值、运行时链路）， 必须写为「结论【待验证：验证方法】」。例：
refund.success 由 payment-service 发出【待验证：查 MQ 控制台生产者】

8. 影响半径方法

影响半径是 Skill 的最终价值落点。采用「双向追踪 + 横向扫描 + 环境评估」三步法。

8.1 双向追踪

方向要问的问题
向上游（谁依赖我）谁调用这个接口/方法/类？谁读我改的表/字段？谁消费我发的 MQ？谁读我改的配置？哪些页面/角色/客户受影响？
向下游（我依赖谁）我调了哪些服务/接口/表/缓存？我改的数据会被谁读？我发的事件谁消费？我改的配置影响哪些实例？

8.2 横向扫描

  • 公共库、基类、AOP、拦截器、过滤器、工具类是否共用？
  • 权限、审计、日志、事务是否被影响？
  • 定时任务、异步线程、重试、补偿、对账是否涉及？
  • 多环境、多租户、灰度、回滚是否兼容？
  • 数据库脚本能否回滚？接口是否向后兼容？

8.3 环境评估

影响半径不止代码，还包括：配置中心、权限模型、发布流水线、监控告警、数据迁移脚本、下游数仓/报表、外部合作方。

8.4 二开推荐流程

需求明确→ 定位功能卡→ 找扩展点→ 填影响半径→ 设计兼容/灰度/回滚→ 实现测试→ 灰度观察→ 更新文档
扩展点优先级
配置 > SPI/插件 > 继承/接口 > 切面 > 改源码。优先在扩展点插入，而不是改主干。

9. 使用示例

9.1 用户输入

我刚接手一个电商平台的后端，代码在 /repo/mall 下。
用 legacy-system-onboarding 帮我梳理一下，重点看下单、支付、退款三条链路，
我要在退款审核上加一个二级审批。

9.2 Skill 行为

  1. 预扫描：识别 Spring Boot 多模块、MySQL、Redis、RocketMQ、xxl-job；运行 scan 脚本得到入口清单。
  2. 定位核心链路：结合入口频次与表依赖，确认下单、支付、退款三条链路，与用户对齐。

12. 避坑清单

#坑后果规避
1一开始读所有代码陷入细节，无法形成整体认知先七层，后深挖
2只信文档和 AI幻觉、过时信息运行时信号交叉验证
3忽略配置、定时任务、MQ、权限、审计影响半径严重低估L0 入口清单强制覆盖
4忽略数据兼容与回滚上线即事故L6 强制填回滚方案
5把菜单当功能地图业务认知残缺L1 必须含角色与链路
6只画静态图不验证图表漂亮但不可信每层附验证清单
7改公共代码当低风险连锁故障横向扫描 + Call Hierarchy
8不更新文档认知资产快速贬值二开后强制回灌
一句话总结
本 Skill 以业务场景为线索，以运行链路为骨架，以功能卡片为索引，以核心表和数据流转为数据地图，以影响半径清单为安全网；用 AI Agent 产出七层结果物，再用运行时信号验证，最终形成能直接指导二开、修改、新增和迭代优化的陌生系统施工图。
