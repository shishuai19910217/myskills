**实验发现（C1 实测）**：圆桌产出的是单模型结构上产不出的边界类型——反例（老舍/海明威）、前提、盲区、约束（如"不得把『作者用了AI』当维度"）；单模型基线是扁平穷举（条数多但无元边界）。因此 C1 成立方向为「**非平面维度覆盖**」，而非简单条数比较。关键提示词修正：必须把**产出目标（objective）**纳入开题并锚定各席位，否则会漂移成对概念的哲学定义。

npm run experiment "问题"      # 单模型 vs 圆桌对照实验

## 1. 背景与目标

### 1.1 问题

用户对陌生领域提问（如"小说AI味表现哪些方面""小说创作技巧"）时，**自己说不清问题的边界和完整维度**，而领域知识其实是 AI 更懂。现有单模型方案（`webnovel-deai-lint`）效果不达预期，存在**覆盖缺口**（漏维度）和**质量缺口**（模式质量差）两类问题。

### 1.2 目标

设计并实现一个 **多模型圆桌勘探 Agent**：当用户输入边界不清晰时，由多个大模型分角色召开"圆桌会议"，通过统筹者地毯式盘问，系统化勘探输入背后的边界与约束，产出**可确认的边界约束清单**，并在此基础上收敛出最终解决方案。用户全程上帝视角掌控（实时旁观、随时插话、可叫停、可循环补充）。

### 1.3 成功标准（可验证）

1. 对同一陌生领域问题，圆桌产出的边界清单在**维度覆盖**上显著多于单模型基线；
2. 用户可对清单补充/修正并循环迭代（补充优化，非新议题）；
3. 用户下发停止信号后，统筹者基于已确认清单生成最终解决方案；
4. 圆桌产出的边界维度可**回灌修订单模型模式库**（质量缺口闭环）。

### 1.4 非目标（Out of Scope，v0.1 不做）

- 紧急秒级问答（单模型直答 + 缓存另行处理）；
- 边界已被领域标准定义死的查询（直接走检索）；
- 多模型**并行**并发流式（v0.1 采用逐轮串行，见 §6.3）；
- 模型训练 / 微调。

## 3. 核心假设与风险

### 3.1 假设

| # | 假设 | 权重 | 不成立时的降级 |
|---|---|---|---|
| H1 | 多模型圆桌比单模型勘探覆盖更全（仅覆盖缺口场景成立） | 1.0（用户明说，需实证） | 回退单模型多角色 + 结构化工序 |
| H2 | 统筹者地毯式盘问优于全自由互动 | 0.3（AI 推断） | 退回自由互动 + 统筹者总结 |
| H3 | 环境能稳定调用多模型，且三来源确为不同模型 | 1.0（文件来源） | 串行轮询 / 减少席位 / 接入真实多厂商 |

| H5 | 附件/链接输入可接入并解析 | 1.0（用户明说，技术待验） | v0.1 仅文本，附件/链接延后 |

### 3.2 风险与缓解（Top 5，对应 Pre-Mortem）

| 死因 | 触发条件 | 概率 | 防死手段 |
|---|---|---|---|
| 多模型假设被证伪 | 对照实验发现覆盖无增益 | 40% | 先实验后开发（§13 里程碑 M0）；证伪即回退 |

## 4. 系统架构

### 4.1 组件图（ASCII）

```
┌─────────────────────────────── 上帝视角 UI（Web/SSE） ───────────────────────────────┐
│  [实时转录区]  [插话输入框]  [停止按钮]  [只看清单切换]  [轮数/token 指示器]           │
└──────────────────────────────────────┬───────────────────────────────────────────────┘
                                       │ 用户消息（插话/补充/停止）
                                       ▼
┌────────────────────────────── 编排器核心（Coordinator Engine） ───────────────────────┐
│  · 状态机（R0-R5）       · 轮次调度（逐轮串行）   · 边界池管理                        │
│  · 分歧裁决             · 收敛判定              · 清单生成/合并                       │
└───────┬──────────────┬─────────────────┬──────────────────────┬───────────────────────┘
        │ 席位1         │ 席位2            │ ...                   │ 席位N
        ▼               ▼                  ▼                       ▼
┌──────────────────────────────── 席位适配层（Seat Adapter） ────────────────────────────┐
│  角色提示词模板  ×  模型绑定（多角色可共享一个模型，C4）                                  │
│  provider 适配：ai2 / omni / volcengine（OpenAI-compatible）                          │
└────────────────────────────────────────────────────────────────────────────────────────┘
        ▲                                          ▲
        │ 输入                                      │ 回灌（质量缺口闭环）
┌───────┴───────────────┐                 ┌─────────┴─────────────────┐
│ 输入接入层              │                 │ 模式库回灌（webnovel-deai-lint）│
│ 文本 / 附件 / 链接       │                 │ 边界维度 → 模式库条目          │
└───────────────────────┘                 └───────────────────────────┘
```

### 4.2 数据流

1. 用户提交输入（文本/附件/链接）→ 输入接入层标准化为「议题包」；
2. 编排器 R0 开题（统筹者复述 + 圈定范围）→ 流式推给 UI；
3. R1 逐轮盘问：统筹者选一个盘问切入点 → 指定席位发言 → 席位返回候选边界条目 → 入边界池 → 流式展示；
4. 发现分歧 → R2 统筹者裁决并记录"分歧标注"；
5. 收敛判定（新增边界 ≤ 阈值 或 用户停止）→ R4 生成边界约束清单；
6. R5 用户审阅：可插话（作为新边界直接入库）或提交补充给统筹者 → 回到 R1（同议题补充优化）；
7. 用户下发停止信号 → 统筹者基于清单生成最终解决方案。

### 4.3 技术选型（建议）

| 层 | 选型 | 理由 |
|---|---|---|
| 语言/运行时 | TypeScript + Node.js | 仓库已有 Node 工具链（package.json） |
| 模型调用 | OpenAI-compatible 直连（对应 `@ai-sdk/openai-compatible`） | 三来源均为 OpenAI-compatible 端点 [来源：opencode.jsonc L5-L29] |
| 实时流式 | Web 单页 + SSE | 上帝视角实时转录最简实现；逐轮串行下 SSE 足够 |
| 会话持久化 | JSON 快照（会议状态可恢复/回放） | 循环补充需要跨轮状态 |
| UI 形态 | Web UI（主）/ 终端 TUI（备） | 上帝视角多区布局更适合 Web |

> **决策 D1**：v0.1 不追求并发流式合并，逐轮串行（C14），SSE 每轮推送一个完整发言块。

## 5. 角色与席位设计（共 6 席，C3/C4）

| 席位 | 角色 | 负责的边界类型 | 统筹者盘问切入点 | 每轮输出格式 |
|---|---|---|---|---|
| 主持 | 统筹者 | 全局：开题/盘问/裁决/收敛/出清单/终局 | — | 盘问指令、裁决结论 |
| 1 | 正向勘探者 | 目标/覆盖边界 | "这个答案至少要覆盖哪些方面？" | 候选边界条目 |
| 2 | 反向勘探者 | 约束/禁区边界 | "有哪些限制或绝对不能触碰的？" | 候选边界条目 |
| 3 | 反例猎人 | 例外/击穿边界 | "如果遇到 XX 反例，这个说法还成立吗？" | 反例 + 受影响边界 |
| 4 | 假设审问者 | 隐藏前提边界 | "这个问题默认了哪些前提？" | 前提假设条目 |
| 5 | 盲区审计员 | 遗漏边界 + 盘问框架审计 | "还有哪些边界所有人都没想到？统筹者问漏了什么？" | 遗漏点 / 框架审计意见 |

**席位绑定规则**：
- 默认每个角色绑定一个模型；可配置为共享（C4）；
- 席位与模型绑定关系存于配置，支持运行时调整（如轮换统筹者模型，防系统性偏置）。

**角色提示词模板（开发基线，每个席位一份）**，统一包含：
- 角色定义与边界类型；
- 输入限制：每次只产 **1 条**最相关的候选边界（防发散）；
- 输出结构：`边界描述 + 理由 + 反例（如适用）+ 可信度（高/中/低）`；
- 铁律：不重复他人已提边界；不给出最终结论（勘探只产边界，不出方案）。

## 6. 会议协议（状态机 R0-R5）

### 6.1 状态机

```
IDLE ──(新议题)──> R0 开题 ──> R1 盘问轮 ──(发现分歧)──> R2 裁决 ──> 回 R1
                                    │
                                    └──(收敛/停止)──> R4 出清单 ──> R5 审阅
                                                              │
                                     (补充/插话)──> 回 R1（同议题）│
                                                              │
                                              (停止信号)──> R5 终局 → DONE
```

事件表：

| 事件 | 触发 | 处理 |
|---|---|---|
| `user_interject` | 用户在任意轮插话 | 作为新边界直接入库 + 供统筹者参考 |
| `supplement` | 用户提交歧义/补充 | 统筹者将其并入议题范围，回 R1（补充优化，非新议题，C5） |
| `dispute` | 角色间意见冲突 | 进 R2，统筹者裁决并记录分歧标注（C16） |
| `convergence` | 连续 N 轮新增边界 ≤ 1 | 统筹者声明收敛，进 R4（C6） |
| `user_stop` | 用户下发停止信号 | 终止勘探，进 R5 终局（C6） |

### 6.2 各阶段细则

- **R0 开题**：统筹者复述议题 → 圈定勘探范围（明确"什么是本题边界""什么超出范围"）→ 向各席位声明盘问顺序。流式展示。
- **R1 盘问轮**：统筹者按「目标 → 约束 → 反例 → 前提 → 盲区」循环选点，逐席盘问（每席每轮 1 条）。每轮结束是插话窗口。
- **R2 裁决**：冲突边界 → 统筹者裁决（支持/否决/合并）→ 产出"裁决结论 + 被否理由"，入清单标注（C16）。
- **R3 收敛判定**：`converged = 最近 N 轮新增边界数 ≤ threshold_N`（C7 完整度优先 → 阈值取宽松，初始建议 N=2、threshold=1，待实验校准）。
- **R4 出清单**：边界池去重 → 归并同维 → 标注来源/可信度/分歧 → 输出「边界约束清单」（模板见 §9.1）。
- **R5 审阅与终局**：用户上帝视角审阅；可补充/修正（回 R1）或停止（统筹者基于清单生成最终方案，模板见 §9.2）。

### 6.3 逐轮串行流式（C14）

- 同一时刻只有一个角色在发言，发言完整块推送（SSE）；
- 每轮结束 = 天然插话窗口，用户可立即介入；
- 不做多模型并发合并流。

### 6.4 分歧裁决与标注（C16）

清单中每个边界条目带状态：
- `一致`：所有发言席位无异议；
- `有分歧`：附 `裁决结论`（统筹者支持/否决/合并）+ `被否理由`。

### 6.5 收敛判定（C6 双通道）

1. **自动**：连续 N 轮新增边界 ≤ 阈值 → 统筹者声明"勘探充分"，征求用户是否进入出清单；
2. **手动**：用户任意时刻下发停止信号。

### 6.6 用户插话与循环（C2/C5）

- 插话内容语义识别为两类：**新边界**（直接入库）或 **补充/歧义**（并入议题，回 R1）；
- 循环是**同议题补充优化**，不是开新议题（C5）；
- 每轮开始前 UI 显示：当前轮数 + 已消耗 token 估算（成本透明，防 C7 失控）。

## 7. 数据模型

### 7.1 输入模型（议题包）

```ts
interface MeetingInput {
  id: string;
  source: "text" | "attachment" | "link";
  content: string;          // 文本 / 附件解析后文本 / 链接抓取后文本
  meta?: {                  // 附件/链接的元信息
    fileName?: string;
    url?: string;
    mime?: string;
  };
}
```

> 附件/链接解析为 v0.1 可延后项（H5），先支持纯文本。

### 7.2 边界条目 schema

```ts
interface BoundaryItem {
  id: string;               // B001...
  type: "目标" | "约束" | "反例" | "前提" | "盲区";
  description: string;      // 一句话
  proposer: string;         // 席位名（或"用户插话"）
  source: string;           // 来源标签（用户原话 / 模型 X / 用户补充）
  confidence: "高" | "中" | "低";
  status: {
    kind: "一致" | "有分歧";
    verdict?: string;       // 统筹者裁决结论
    rejectedReason?: string;
  };
  counterExamples: string[];
  dedupKey: string;         // 去重哈希键
}
```

### 7.3 清单结构

```ts
interface BoundaryList {
  meetingId: string;
  topic: string;                  // 复述后的议题
  scope: string;                  // 勘探范围声明
  items: BoundaryItem[];          // 按类型分组
  rounds: number;                 // 实际轮数
  convergence: "auto" | "user_stop";
  disputesResolved: number;
  tokenEstimate: number;
}
```

### 7.4 会议快照（会话持久化）

```ts
interface MeetingSnapshot {
  meetingId: string;
  state: MeetingState;            // R0-R5
  boundaryPool: BoundaryItem[];
  roundNumber: number;
  coordinatorHistory: string[];   // 盘问历史，供补充优化参考
  userInterjections: string[];
  createdAt: string;
  updatedAt: string;
}
```

> 快照用于：循环补充的上下文延续、会议回放、失败恢复。

## 8. 用户交互设计

| 能力 | 说明 | 对应约束 |
|---|---|---|
| 上帝视角 | 实时转录全部发言，逐轮追加 | C2 |
| 随时插话 | 任意轮结束后输入框可用；语义识别为"新边界"或"补充" | C2 |
| 停止信号 | 显式停止按钮，立即终止勘探进入终局 | C6 |
| 只看清单 | 一键切换为「边界约束清单」视图 | C17 |
| 折叠 | 上帝视角可折叠某席位/某轮历史 | C2 防过载 |
| 成本指示 | 每轮显示轮数 + token 估算 | C7 防失控 |

**插话语义识别**（建议用统筹者本地判定）：
- 直接给边界/维度 → 新边界入库；
- 给歧义/补充/反问 → 并入议题，回 R1；
- 无法判定 → 询问用户归属，不擅自处理。

## 12. 回灌机制（质量缺口闭环，C15）

- **方向**：圆桌产出的边界清单（目标/约束/反例/前提/盲区）→ 转换为 `webnovel-deai-lint` 模式库新增条目（模式编号、识别规则、方向指引）；
- **循环**：清单更新 → 模式库增补 → 单模型 lint 质量提升 → 反馈到下一次圆桌的盘问切入点；
- **触发**：每次会议结束、且用户确认清单有效后，可选执行回灌（需用户确认，避免污染模式库）。

## 13. 开放问题与待验证项

1. **provider 同源性**：三来源是否真为不同模型（M0 实测）；
2. **收敛阈值**：`N=2, 新增≤1` 是否过早/过晚收敛（M5 调优，C7 取宽松）；
3. **插话语义识别**：新边界 vs 补充的分类准确率（M3 后实测）；
4. **轮数/成本上限**：是否设置硬上限（C7 接受多轮，但防失控需上限）；
5. **统筹者模型轮换**：是否作为默认策略（H2/H3 验证后定）。

## 14. 明确不适用场景（NOT Applicable）

1. **紧急快速问答**：多轮会议超时 → 用单模型直答 + 缓存；
2. **边界已被领域标准定义死**：如"Python list.append 语法" → 直接检索，不走会议；
3. **用户无时间/意愿旁观会议** → 静默跑完只出清单模式。
