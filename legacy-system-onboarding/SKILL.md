# legacy-system-onboarding

## 何时使用

**触发**：用户要接手陌生/遗留系统、要"看懂这个项目/系统长什么样"、要还原某功能的完整实现与链路、要评估改动某功能会影响什么、要做开发交接。

**不触发**：代码评审（只评价已写代码）、重构或修 bug 的执行、单纯跑测试、写新功能、性能压测、纯问答式的代码咨询（无分析文档产出需求）。

**一句话定位**：把"读代码"变成"可追溯、可核验、可持续更新的系统认知资产"。扫描完成、图谱生成、文档已生成，都不等于系统已被理解。

## 执行前必读

- 判定模式与产出：本文 §1、§2
- 做任何结论前：`references/evidence-and-confidence.md`（证据分级、推断边界、证据等级≠运行时确定性）
- 写文档前：`templates/` 下对应模板
- 收尾验收：`references/quality-acceptance.md`（覆盖率定义、验收门禁、状态判定）

## 1. 执行模式

只允许两种模式。

### 模式 A：全量分析

**适用**：用户要全面了解项目/整个系统；需要建立或重建系统级认知基线；既有全局分析已过期或架构已变。

**必须产出**：`01-系统全貌.md`、`02-系统深度分析.md`

### 模式 B：专项分析

**适用**：用户指定某功能、业务链路、API、消息入口、类、方法、模块或一组相关功能；要求分析实现、排障、开发影响或维护方式。

**默认产出**：`功能详细设计-<功能名称>.md`（文件名去除系统非法字符，勿覆盖无关文档）

### 通用机制

增量更新、断点恢复、分批处理、工具降级**不是独立模式**，A/B 都适用，见 §7、§8。

用户意图明确时直接执行，不在每个阶段请求确认。只有缺失信息确实阻止继续且无法从项目证据推断时，才提一个最必要的问题。局部不确定性优先继续分析并登记为待验证项。

## 2. 核心约束

1. 以实际工作区、源码、配置、SQL、接口定义、测试、日志和已有文档为依据。
2. 不编造不存在的文件、类、方法、接口、表、字段、消息主题、状态或调用关系。
3. 区分源码事实 / 工具发现 / 上下文推断 / 待验证，写清证据等级与适用边界。
4. 保留文件路径与稳定代码定位；行号会漂移，只作辅助，不作唯一身份。
5. 关键结论必须双向核验（正向追踪 + 反向检索），不得只沿单条调用路径推断全貌。
6. 工具不可用时降级到源码检索、构建文件、静态分析、测试等手段，并在交付中记录降级；不得静默跳过关键分析。
7. 不执行与分析无关的破坏性操作；不修改业务源码，除非用户明确要求。
8. 凭据、令牌、密码、个人信息不原样落入文档，只记配置键与脱敏说明。
9. 不把推测写成已验证结论，不用"系统应该是这样"替代证据。
10. 产出服务后续检索、维护与增量更新，不追求篇幅。

## 3. 启动与基线

1. 确认工作目录、仓库边界、用户指定范围。
2. 判定工程形态：单体 / 多模块 / 微服务集合 / 前后端分离 / 混合仓库。
3. 记录代码基线：优先 Git commit + 分支 + 工作区状态；无 Git 则记目录、文件时间等替代基线并说明局限。
4. 检查已有 `01-系统全貌.md`、`02-系统深度分析.md`、功能详细设计及历史分析产物——**它们只是待核验的历史知识，不是当前代码事实**，须抽查关键结论与源码一致性。
5. 探测可用工具：CodeGraph、Graphify、语言服务、构建工具、源码检索、SQL 与接口解析。先确认可用性，不假设已安装或命令名固定（策略见 §6）。
6. 建立执行记录：模式、范围、基线、已完成阶段、失败项、下一步（断点恢复用，格式见 §8）。

## 4. 扫描范围与资产登记

按项目实际扫描登记：源代码与生成代码 / 前端路由、页面、组件、状态管理、API 封装 / 后端应用、模块、包、类、方法 / 构建配置、依赖清单、运行与部署描述 / 迁移脚本、DDL、SQL、ORM 映射 / REST、RPC、OpenAPI、IDL 与接口契约 / 消息主题、生产者、消费者、监听器、回调 / 定时任务、批处理、后台线程、异步执行 / 权限、认证、租户、配置中心、特性开关 / 单元、集成、契约测试与测试数据 / README、设计文档、运维文档。

每个对象必须落在以下状态之一：**已扫描 / 已分析 / 已验证 / 明确排除 / 工具或权限导致未扫描 / 已识别未分析**。

二进制、依赖缓存、构建产物、第三方库、自动生成代码可按分析价值决定深度，但必须写明排除或抽样规则。**不得把排除项伪装成已分析项。**

## 5. 功能识别与五维模型

### 5.1 组织方式

**有前端**：按"端 → 业务功能"组织（Web / APP / 小程序 / 其他形态按实际登记）。每个功能关联页面、路由、组件、API、后端接口、业务服务、数据对象、外部依赖。多端共用同一后端能力时分别记录端侧入口并标记共享实现。

**无前端**：按实际工程结构组织（微服务、应用、包/模块、技术分层、技术入口、可从源码证据识别的业务功能）。不得因为无前端就只输出包名与技术分层——仍需从接口、方法、数据模型、消息、业务规则中识别后端功能。

**功能识别原则**：页面、接口、表、类通常是功能的组成部分，未经分析不得各自登记为独立业务功能；一个功能可有多个入口，一个入口也可服务多个功能；链路可跨模块、应用、线程、消息系统和外部服务；边界不清时给出暂定边界及依据并登记待验证项。

### 5.2 五维分析

两模式共用五维，通过统一 ID 连接。每维都有完成判据，未达判据即登记为分析缺口。

| 维度 | 要回答的问题 | 完成判据 |
|---|---|---|
| 功能模块 | 职责、边界、子功能、调用方、入口、输出、关联代码、数据对象、上下游、共享能力 | 该功能的边界有一句可辩护的界定，且入口已穷举（含非页面入口） |
| 业务链路 | 触发条件、端到端步骤、分支、异常路径、异步、重试补偿、终点 | 每条关键链路追踪到业务终点，或明确写出为何无法继续 |
| 代码实现 | 文件、类、方法、接口、调用顺序、参数、返回值、关键判断、异常处理、事务边界、异步、外部调用 | 每个重要步骤都有可定位的证据位置 |
| 数据与状态 | 输入来源、转换规则、表/字段/SQL、缓存、消息、输出副作用、状态集合、迁移条件、持久化、事务、并发、一致性 | 关键字段的写入点与读取点都已反向核验；无独立状态机时明确说明而非硬画状态图 |
| 开发影响 | 直接/间接依赖、共享组件、接口契约、跨端联动、数据兼容、权限、配置、异步任务、外部系统、风险、回归范围 | 修改点的上下游影响有证据，回归范围可执行 |

### 5.3 IPO

对关键步骤标注输入、处理、输出。**输出不等于接口响应**：数据库变更、状态迁移、缓存更新、消息发布、通知及其他副作用同样是输出，必须列出。

### 5.4 深度分配

关键链路（入口、关键分支、异常、异步、数据、状态、终点、影响范围全深挖）；普通功能（至少登记功能、入口、主要实现、关键数据、直接依赖，未深入部分明确标记）；基础资产（登记职责与关系，若被关键链路使用或影响面大则递归深入）。

按业务重要性、依赖关系、数据关联、风险分配资源，**不按代码行数机械分配**。

## 6. 关系发现与工具策略

1. 探测 CodeGraph、Graphify 或同类工具是否存在、可运行、是否支持当前语言与工程结构。
2. 用可用工具发现文件、类、方法、调用、依赖、影响范围。
3. 用源码、构建配置、框架约定、SQL、接口定义、测试、日志交叉核验关键关系。
4. 对反射、依赖注入、动态路由、框架自动装配、消息订阅、回调、异步任务、运行时配置保持警惕：**静态调用图里没有，不代表关系不存在**。
5. 工具输出只是证据来源之一，不自动等于已确认事实。
6. 工具失败要记录工具名、失败现象、影响范围、替代方法，然后继续。
7. 不为用工具而用工具。只有当工具显著提升关系发现、覆盖统计或核验效率时才采用。

常见语言的入口与隐式关系识别清单见 `references/discovery-playbook.md`。

## 7. 链路追踪

**正向**：入口 → 参数/身份/权限/上下文 → 校验与业务规则 → 核心处理 → 关键分支与异常 → 数据读写与状态变更 → 事件/消息/定时/异步 → 外部调用与回调 → 最终输出、副作用、业务终点。

**反向**：从关键表、字段、状态更新、消息、外部调用、关键方法反查——谁读写它、哪些入口能触发、哪些功能依赖它、是否存在未纳入分析的入口或隐式依赖。

**增量更新**（A/B 内部机制）：
1. 比对当前基线 vs 文档记录的基线。
2. 识别变化面：文件、类/方法、调用关系、接口契约、表字段与 SQL、状态逻辑、消息任务、配置。
3. 判定直接与间接影响范围。
4. 重分析受影响对象及必要上下游——**不能因为某文件未变就认为其语义未变**。
5. 更新文档、关系索引、证据、覆盖统计，保持 ID 稳定。
6. 影响无法界定、核心架构变化、全局关系明显失效时，建议或执行全量复核。
7. 记录变更摘要、受影响对象、重分析范围、仍未验证项。

## 8. 断点恢复

分批执行或中断前，把以下内容写入工作区内的临时状态文件（不作为 Skill 固定目录，也不混入业务文档）：

模式与目标范围 / 代码基线 / 已扫描·已分析·已验证对象 / 已生成或更新文档 / 已完成与未完成链路 / 工具失败与降级 / 待验证项 / 下一步计划。

恢复时**先检查基线是否变化**，变了就重评相关对象，不得盲目复用过期中间结果。

## 9. ID、关系与证据

**ID 前缀**：`SYS-` 系统/应用｜`MOD-` 模块｜`FUN-` 功能｜`ENT-` 入口｜`FLOW-` 业务链路｜`STEP-` 链路步骤｜`CLS-` 类或代码实体｜`MTH-` 方法｜`API-` 接口｜`TAB-` 数据表｜`FLD-` 字段｜`STM-` 状态机｜`MSG-` 消息/事件｜`EXT-` 外部依赖｜`RISK-` 风险｜`VER-` 待验证项。

ID 跨文档稳定，增量更新不得随意重编号；对象边界或身份变化时记录变更关系。

**关系类型**：`contains`、`implements`、`calls`、`depends_on`、`triggers`、`publishes`、`consumes`、`reads`、`writes`、`transitions`、`invokes_external`、`affects`、`verified_by`、`evidenced_by`。只记录有证据支持或明确标记为推断的关系。

**证据等级 E1–E5、每项结论应记录的字段、待验证项必填内容** → `references/evidence-and-confidence.md`

## 10. 执行步骤

### 模式 A

1. 检查边界、基线、已有文档、工具能力。
2. 扫描登记源文件与技术资产。
3. 识别语言、工程结构、应用、微服务、模块。
4. 按 §5.1 识别业务功能、技术入口、多端关系。
5. 建统一 ID 与初步关系索引。
6. 用图谱、源码检索、静态分析补全关系。
7. 按重要性与风险选关键链路并定深度。
8. 关键链路正反向追踪：代码、数据、状态、异步、异常、终点。
9. 登记普通功能与基础资产的状态与缺口。
10. 按 `templates/01-系统全貌模板.md`、`templates/02-系统深度分析模板.md` 生成两份文档。
11. 核对两份文档的 ID、模块、功能、链路、统计口径一致性。
12. 执行 §11 质量验收，修复可修复缺陷，更新验收结果。
13. 交付：文档、覆盖统计、待验证项、工具降级记录、代码基线。

分工：全貌文档负责结构、功能地图、主链路、入口、核心数据、外部依赖、覆盖统计与导航；深度分析文档负责五维细节、关键链路、具体代码、数据与状态、依赖关系、证据与分析缺口。

### 模式 B

1. 识别目标功能与输入方式，记录基线。
2. 有全局文档则先读并核验相关部分；没有则不虚构全局认知。
3. 定目标范围与上下游边界。
4. 识别全部相关入口（页面 / API / 消息 / 事件 / 定时任务等）。
5. 正反向追踪。
6. 分析关键调用、分支、业务规则、异常、事务、异步。
7. 追踪表、字段、SQL、缓存、消息、状态变化与副作用。
8. 分析接口契约、外部依赖、权限、并发、幂等、一致性。
9. 递归分析必要依赖，给出开发影响与回归范围。
10. 按需生成流程图、调用链图、数据流/状态图、UML。
11. 按 `templates/03-功能详细设计模板.md` 生成文档。
12. 执行 §11 专项验收，修复可修复缺陷。
13. 把新发现的系统级事实、关系、待验证项回写全局文档；无全局文档时记为可复用的专项发现，**不得宣称已更新全局基线**。
14. 交付文档、证据、验收结论、遗留事项。

## 11. 验收

覆盖率指标定义与统计口径、两套验收清单、验收状态判定 → `references/quality-acceptance.md`。

硬性底线（无需查参考即可执行）：
- 覆盖率必须写明分母来源、统计时点、排除规则、失败对象；分母不可靠就写"无法准确统计"并说明原因，**不得编造百分比**。
- 覆盖率不能单独证明系统已被理解。
- 验收结论必须附依据、剩余风险、下一步建议。
- 不得只回复"完成"。无法访问、写入或验证目标路径时如实说明，不伪造文件或链接。

## 12. 文档与图表

- Markdown 用清晰层级、表格、代码定位、导航。
- Mermaid 图必须与正文和证据一致，**不为图形完整虚构关系**；图过大拆成多张有明确范围的图。
- 关键图表：总体架构、模块依赖、关键业务链路、调用链、数据流、状态流转、必要的 UML。
- 不适用的图说明不适用原因；证据不足的图标记待验证边界。
- 文档须写明分析范围、代码基线、生成/更新时间、覆盖统计口径、已知限制。
- 关键结论尽量挂到统一 ID 与代码定位。

## 13. 失败处理与执行预算

| 情形 | 处理 |
|---|---|
| 工具不可用 | 记录失败，改用可行替代手段 |
| 源码不完整 | 分析可见部分，写明缺失范围与结论边界 |
| 外部系统不可访问 | 只分析本系统可见的调用契约，不推断外部内部实现 |
| 关系存在歧义 | 保留候选关系并标待验证 |
| 项目过大 | 按模块与链路分批，维护统一 ID 与断点记录 |
| 预算耗尽 | 优先关键链路与高风险对象，登记未完成项，**不得声称已全量深度分析** |
| 验收失败 | 只修高影响可定位问题，设有限修复轮次；到预算就输出实际状态与剩余问题，不无限循环 |
| 发现敏感信息 | 文档内脱敏，不复制秘密值 |

## 14. 最终交付格式

1. 执行模式与分析范围
2. 产出/更新的文件及路径
3. 主要分析结果
4. 覆盖指标及统计限制
5. 验收状态与依据
6. 未解决问题、风险、建议下一步
