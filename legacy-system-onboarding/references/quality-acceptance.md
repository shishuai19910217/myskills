# 质量验收

交付前读本文件。验收的目标不是"看起来完整"，而是**让读者能判断哪些结论可信、哪些还没验证**。

## 1. 覆盖指标

按适用情况统计，每项都要写清分母来源、统计时点、排除规则、失败对象。

| 指标 | 计算方式 |
|---|---|
| 源文件扫描覆盖率 | 已扫描源文件数 / 纳入范围源文件总数 |
| 方法分析覆盖率 | 已按要求分析的方法数 / 需要分析的方法总数 |
| 入口分析覆盖率 | 已分析入口数 / 已识别且纳入范围的入口总数 |
| 功能登记覆盖率 | 已登记功能数 / 已识别功能总数 |
| 关键链路完成率 | 已到业务终点或已明确验证边界的关键链路数 / 已识别关键链路总数 |
| 关键关系证据覆盖率 | 有可追溯证据的关键关系数 / 纳入核验的关键关系总数 |

分母不可靠时写"无法准确统计"并说明原因。**不得编造百分比。** 覆盖率是自检工具，不是完成度证明。

## 2. 模式 A 验收清单

- [ ] 扫描范围、排除项、失败项明确
- [ ] 应用、模块、功能、入口均已登记
- [ ] 功能组织方式符合实际工程形态（不是只有包名和技术分层）
- [ ] 关键链路到达业务终点，或已明确写出验证边界
- [ ] 关键代码、数据、状态、异步关系均有证据
- [ ] 架构图、依赖图与正文一致，无凭空关系
- [ ] 两份系统文档的 ID 与统计口径一致
- [ ] 覆盖率、待验证项、工具降级记录完整

## 3. 模式 B 验收清单

- [ ] 目标与范围（含不做什么）清晰
- [ ] 相关入口已识别，含非页面入口
- [ ] 调用链覆盖关键分支、异常、异步
- [ ] IPO 写明了输入、处理、输出**及副作用**
- [ ] 相关表、字段、SQL、状态变化已追踪，写入点有反向核验
- [ ] 接口、外部依赖、事务、并发、幂等风险已检查
- [ ] 开发影响与测试建议有证据支撑
- [ ] 待验证项与专项发现回写记录完整（无全局基线时明示未回写）

## 4. 验收状态

| 状态 | 判定条件 |
|---|---|
| 通过 | 关键质量条件满足，剩余缺口不影响声明的交付范围 |
| 有条件通过 | 主体完成，剩余缺口已披露且可接受——必须列出缺口与影响 |
| 未通过 | 关键链路、证据或覆盖要求未满足 |
| 无法完成验收 | 受权限、源码缺失、工具或环境限制，拿不到足够证据 |

结论必须附：依据、剩余风险、下一步建议。

## 5. 交付前自检（3 分钟版）

如果时间紧，至少确认这四件事：

1. 有没有一句话能说清"这个系统的核心链路是什么"？说不清说明分析没收敛。
2. 文档里每个"系统会……"的句子，能否指到具体文件位置？
3. 待验证项里每条是否都有一个可执行的验证动作？
4. 有没有哪张图是照着模板画的、而不是照着代码画的？
