# 证据分级与置信度

写任何结论前读本文件。核心规则：**证据等级描述的是"这条结论有多可靠的来源支撑"，不是"这段代码在生产环境一定被执行"。**

源码证明存在某段逻辑，不等于证明生产环境执行了该逻辑。静态可达性、配置开关、灰度、租户差异、数据条件都可能导致该分支从未生效。

## 证据等级

| 等级 | 含义 | 可作为什么用 |
|---|---|---|
| E1 | 源码、SQL、配置、接口定义直接证据 | 可直接断言事实，但只断言"代码如此" |
| E2 | 多个来源交叉印证（如源码 + 测试 + 日志） | 强度高于 E1 单项，适合作为关键结论主证据 |
| E3 | 静态分析或图谱工具发现 | **尚需结合风险核验**，不得单独支撑高风险结论 |
| E4 | 上下文推断（命名约定、同构模块、框架惯例） | 只能写成推断，必须登记后续验证方式 |
| E5 | 证据不足 | 只能进待验证台账，不得出现在结论段落里当作事实 |

## 每项关键结论应记录

- 结论本身（一句可证伪的话）
- 关联对象 ID（SYS/MOD/FUN/FLOW/STEP/CLS/MTH/API/TAB/FLD/STM/MSG/EXT/RISK/VER）
- 文件路径
- 类 / 方法 / SQL / 配置位置
- 证据等级
- 适用边界（哪个租户、哪种配置、哪个版本、哪个分支条件）
- 不确定性说明

## 待验证项台账（必填字段）

| 字段 | 要求 |
|---|---|
| ID | `VER-xxx`，跨文档稳定 |
| 问题描述 | 一句能直接回答的疑问，而非"这里不确定" |
| 关联对象 | 相关模块、功能、链路、代码 ID |
| 业务影响 | 这个未知项会影响什么决策 |
| 优先级 | 高 / 中 / 低，按业务影响定，不按好奇心定 |
| 当前缺少的证据 | 缺日志？缺配置？缺外部系统访问？缺业务方确认？ |
| 验证方法 | 具体到可执行：查哪张表的哪条记录、问哪个角色、跑哪个用例 |
| 关闭条件 | 什么情况下可以认为它被解决了 |
| 状态 | 开放 / 验证中 / 已关闭 / 无法验证 |

## 常见误用

- 把 E3 工具输出直接写成"系统调用 X"——工具看到的是静态引用，不是运行时调用。
- 把未见调用当作"不存在调用"——反射、DI、动态路由、消息订阅、回调、框架自动装配都可能隐藏关系。
- 用"根据命名推断"填补缺失证据却不标 E4。
- 覆盖率 100% 就宣称系统已被理解——扫描覆盖 ≠ 语义理解，报告里必须同时给出分析缺口。
- 待验证项写成"需要进一步确认"，没有可执行的验证方法，等于没登记。
